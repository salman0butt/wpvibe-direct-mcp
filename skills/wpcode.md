# WPCode

Start with `discover_abilities` for the `wpcode` namespace. Current verified WPCode abilities are read-oriented: list snippets, detect snippet errors, read error logs, search the WPCode library and read settings. Inspect them with `get_ability_info` and call them with `run_ability`. For a new or edited PHP/JS/CSS snippet, use Direct MCP `code_snippet` instead of writing WPCode storage yourself: the native dormant classification saves new executable snippets disabled, and writes that fail dormant checks require the Direct one-time administrator approval flow. Never edit WPCode storage through raw SQL or generic REST.

With WPVibe 1.20.4+, `code_snippet` also supports `action: "deactivate"` with an existing positive integer `id` for WPVibe-created snippets (no approval required); `action: "delete"` moves an unchanged WPVibe-created snippet to WPCode's trash **only after one-time administrator approval**, unless the site owner explicitly enabled dangerous approval bypass. The ID must be an integer or canonical positive decimal string: negative, fractional, prefixed and coerced IDs are rejected so a different snippet cannot be targeted silently. For both retire actions omit `code`, `title`, `code_type`, `location`, and `insert_method`; the handler rejects attempts to retire snippets that WPVibe did not create, and deletion refuses code modified by someone else. Do not use these actions against older WPVibe versions. A human must still enable/re-enable snippets in WPCode's wp-admin interface. If WPCode's execution-cache state is uninspectable or still contains the retired snippet, Direct returns `snippet_cache_still_active` instead of claiming success. After an upstream error, inspect actual snippet state and WPCode cache before retrying a write to avoid repeating side effects.
