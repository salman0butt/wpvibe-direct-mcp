# Divi / Divi 5

Use WordPress/WPVibe content and meta operations that preserve Divi's native storage instead of inventing a separate Direct-MCP Divi format. For ordinary Divi pages, inspect the post first, use `search_content` / `edit_content` for surgical changes to the stored builder content, and verify the rendered page afterward. WPVibe's content path calls Divi refresh hooks such as `et_divi_save_post` and `et_theme_builder_clear_wp_post_cache`, so a successful content edit also refreshes Divi excerpts/styles and Theme Builder consumers.

For Divi Theme Builder headers, footers, and body templates, read the existing template posts and linkage meta before changing anything. WPVibe added multi-value `post meta add` / `post meta delete <id> <key> <value>` support specifically so Divi's Theme Builder linkage rows can be appended or removed without `post meta update` destroying sibling rows. Use `run_wp_cli` to list/get the current meta, preserve every existing row, and append only the required relationship with `post meta add`; never replace an unknown multi-value key wholesale. Edit the actual template post content with `edit_content`, then re-read the linkage meta and inspect pages that inherit the template to confirm the header/footer/body and styles refreshed correctly.

Divi site-wide presets/options can restyle many pages at once. Read the complete current value first and rely on WPVibe's approval gate for protected/global builder settings, options, or SQL paths. Prefer documented Divi/WordPress APIs or installed Abilities whenever the site exposes them. Do not write opaque serialized builder structures, private database rows, or guessed Divi 5 internals merely to imitate the editor.
